> 上表为实施前状态。2026-10-22 两批实施后（见第 2 节“第二批实施记录”）：预算 54 条中 42 条已覆盖、6 条部分覆盖、3 条词表提示+AI 复核、3 条由下载环节/上传入口判定；决算为 47 / 2 / 2 / 3；未完全覆盖的条目均已带处置决议（见第 2 节“第三批决议”）。逐条状态见 CSV“2026-10-22实施后状态”列与 `rules/checklists/`。

要点：

1. **决算的数据勾稽基本到位，预算的数据勾稽明显偏弱。** 决算 16 条勾稽中 11 条已覆盖；预算只有 3 条。预算缺的主要是：类→款→项层级加总（C-02）、收入预算总表 T2 完全没有勾稽（C-07）、财政拨款收支总表三列对 T5/T6/T7（C-04）、编制说明分项加总（C-10/C-11）。这些在决算侧都有现成实现（`native_hierarchy_checks`、`V33-005` 等）可以移植。
2. **“完整性”维度两边都弱。** 现有规则查的是“表在不在”，几乎不查“报告章节和要素在不在”：主要职能、机构设置、名词解释、项目经费情况说明、其他相关情况说明的 5 个小节、决算四大部分、国有资产占有使用情况，都没有检查。
3. **文字规范有规则，但词表很窄，而且预决算不对称。** 例如 `CMM-002` 只认“预算预算/决算决算/财政拨款财政拨款”3 个重复词；`V33-113` 的标点和单字重复检查只作用于决算；模板残留只认“增加（减少）”。
4. **格式规范与公开合规完全没有**，需要另外两种能力：版面视觉（空白页、横向页、彩色底纹）和材料台账元数据（公开日期、文件格式）。台账侧已有截止时间和发布时间字段（`material_slot_status.py`），可以直接接。
5. **有 5 处现有口径会让清单案例被“静默放过”**，已于 2026-10-22 定下决议：清单直接作为全系统检查指标（第 2 节）。

## 3. 融入方案

### 3.1 三层结构：清单层 → 义务层 → 规则层

现有的检查义务台账（`check_obligations.py`）本来就是为“应检查的事项”设计的，而且有一条关键纪律：**规则还没实现的要求，用 `pending_checkers` 显式记成 `not_implemented`，不能静默当作通过**。清单最适合挂在这一层上。

```
清单层（新增）  rules/checklists/putuo_budget_v1.yaml / putuo_final_v1.yaml
   │  每条：id（PTB-A-01 / PTF-A-01）、维度、检查点、合格标准、案例、obligations[]
   ▼
义务层（现有）  check_obligations.OBLIGATION_CATALOG
   │  每个清单条目映射到 ≥1 个 Obligation；暂无实现的新建 Obligation + pending_checkers
   ▼
规则层（现有）  budget_rules / rules_v33 / common_rules
```

具体做法：

1. 两份 xlsx 继续作为业务人员维护的主文件；写一个转换脚本生成清单 YAML，版本号跟随清单（v1.0 → v1.1）。
2. 给 `Obligation` 增加 `checklist_refs` 字段，或在清单 YAML 里写 `obligations`（二选一，建议后者，免得改动义务结构）。
3. 加一个测试：**清单每一条都必须映射到至少一个义务**；没有实现的义务必须带 `pending_checkers`。这样台账的完成率会如实反映“普陀清单还有多少条没实现”，不会被规则数量绿化。
4. 问题输出增加“对应清单条目”（例如“预算 B-06 正文金额与预算表一致”），审校报告可以按清单的六个维度汇总，和人工检查表对得上。

### 3.2 全系统默认口径（不设区域 profile）

按 2026-10-22 决议，本清单直接作为整个系统的检查指标，不为普陀单独设一套口径。原先计划放进区域 profile 的内容全部改为系统默认：

- 封面模板：“上海市××区××年区级部门（单位）预算”“××年度部门决算”，“预算主管部门/预算单位”标注；区名与单位全称取自组织台账，不写死“普陀区”
- 章节模板：部门预算 7 章 / 单位预算 6 章 / 决算四部分，以及“其他相关情况说明”的 5 个小节
- 必备表：预算、决算 9 张表全部必备（含空表）
- 容差：通用 0.01 万元 + 取整包络；元→万元换算精确比对
- 主体用语：“区级预算主管部门”“区级财政”
- 公开截止日：按年度配置在材料台账（不写死 2026-02-15 等日期）

这些默认值同步写进 `AGENTS.md`，保持它作为便携规则文件的自包含。

### 3.4 案例变成回归样例

两份清单的“常见错误表现”合计约 200 个具体案例，大多带单位名和原文片段，是很好的回归素材：

- 每个案例做成一条正例（原文片段 + 应命中的规则 + 清单编号），并配一条对应的正确写法作为反例，防止误报；
- 参数化测试断言：每个案例要么被对应规则命中，要么所属义务处于 `pending_checkers`（显式未实现）；
- 格式参照 `docs/GOLDEN_CORPUS_TEMPLATE.md`。
