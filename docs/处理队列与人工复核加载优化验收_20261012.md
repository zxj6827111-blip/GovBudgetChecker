# 处理队列与人工复核加载优化验收

## 结论

上次新增人工复核清单和侧栏待办角标时，引入了性能回归。根因是把完整详情加载用于批量权限检查与问题决定快照，再由多个组件重复发起全量请求。现已修复本地实现，保留清单选择、显式开始复核、版本绑定和服务端完成门禁。

## 原因与修改

- 23 份材料的一次清单查询，原先发生 115 次 `get_job_status_payload` 调用：23 次权限检查，加上每份材料 4 次问题快照内部读取。该函数会补充 AI 证据位置、读取 PDF、复制结果和重建报告。性能采样显示主要耗时在这些读取及 PDF 文本提取，数据库与健康检查正常。
- 权限检查改为只读原始任务归属，保留组织绑定优先级与上传者权限；状态损坏或任务不存在仍拒绝访问。
- 问题快照在同一把文件锁内只投影一次；没有人工决定的任务不加载完整详情。已有决定仍使用原有版本、指纹匹配规则，CAS token 的算法与内容保持一致。
- 任务文件扫描和复核问题摘要计算移到线程池，避免阻塞异步事件循环。
- 侧栏和页面共享正在进行的列表请求，切换栏目不再重新挂载侧栏请求。已完成响应不持久缓存；写入后取消旧读取并重新查询。清单保留周期刷新、焦点刷新和手动刷新。
- 客户端请求最长等待 15 秒；读取失败明确提示重试，已有清单保持可见并标注上次成功数据，未知角标不显示为零。

## 性能证据

使用本地真实数据库的只读事务，在独立诊断进程中运行旧/新清单读取。未使用账号凭据，未开启或完成任何真实复核，未修改开发服务缓存。旧忽略文件待迁移时脚本会拒绝执行。

| 场景 | 清单查询耗时 | 完整详情读取次数 |
| --- | ---: | ---: |
| 旧流程 | 25.84 秒 | 115 |
| 优化后，定位缓存未预热 | 3.33 秒 | 3 |
| 优化后，后续读取 1 | 0.88 秒 | 3 |
| 优化后，后续读取 2 | 0.77 秒 | 3 |

四次响应整份 JSON 的 SHA-256 完全相同；当前 23 份材料中待复核 12 份、复核中 11 份。此对比包含材料信息、各项计数及复核状态，不只比较总数。

真实已登录的本地浏览器中，无接口拦截地切换两个栏目，点击到目标列表可见均约 3.1 秒。该数字包含浏览器自动化调用开销，前端运行于 Next 开发模式，不等同于线上浏览器纯渲染耗时。

证据位于 `artifacts/review-list-performance-20261012/`：

- `comparison.json` / `compare_reads.py`：正式只读对比及可复现脚本。
- `worklist-profile.txt`：旧流程性能采样；采样自身会增加耗时，不能把其 66 秒当作普通查询耗时。
- `live-ui-receipt.json` / `live-review-list.jpg`：真实登录页面验收。
- `task-change.patch` / `changed-paths.json`：本次修改相对修改前工作区的差异，保留仓库原有改动。其中服务文件基线仅反向去除本次新增的线程池调用两处改动。

## 验证

- 104 项相关 Python 测试通过，包含任务权限、清单状态、问题快照、复核门禁和工作流。
- 42 项浏览器回归通过，包含请求数量、栏目切换、筛选返回、显式开始复核、失败恢复、失效版本及导航。
- 队列运行/批量提交相关浏览器用例另跑 13 项通过，其中 10 项与前述重复，合计 45 项不同用例通过。
- 请求合并/取消/超时、任务列表事件、复核清单适配器和轮询单元检查通过。
- TypeScript、ESLint、Ruff 与隔离目录中的 Next 生产构建通过。构建没有清除正在运行的开发服务缓存。
- 本地后端 `/health`、`/ready` 返回 200。

验证范围是当前本地 23 份材料；没有做生产环境或大规模并发压测，没有将开发库用作写入型 PostgreSQL 测试库。

## 回退与后续

本次没有数据库迁移。若需回退，应仅按 `task-change.patch` 撤销本次改动，保留已有页面改造和其他用户修改。服务文件变化通过模块热重载生效，浏览器刷新可确保加载新客户端代码。

后续材料量显著增长时，先复测性能，再按证据决定是否改为服务端分页及独立角标查询。
