## 验收入口

从仓库根目录执行：

```bash
.venv/bin/python scripts/run_zc07_acceptance.py \
  --manifest /path/to/zc07-dataset.json \
  --e2e-evidence /path/to/zc07-e2e-evidence.json \
  --mode legacy \
  --output outputs/zcode_remediation/ZC-07/acceptance.json
```

不带清单时执行只读预检：检查当前语料库存、测试数据库变量、Docker daemon 和 OCR 模型清单；输出 JSON，必定以非零退出，因为没有完整冻结数据集和真实 E2E 证据。脚本不启动容器、不连接数据库、不改写 `corpus/`、`uploads/` 或历史任务目录。报告只记录数据库变量是否配置，不记录连接串。

## 冻结数据集清单

清单为 UTF-8 JSON。所有文档都必须有同名 `corpus/<doc_id>/golden.json` 和唯一、哈希匹配的原始 PDF；不能以缓存解析文本代替原件。`golden.json` 必须有 `truth_frozen_at`、非空 `reviewed_by` 和标签。`replay_path` 指向同一 doc_id / PDF SHA 的实际生产链回放结果。

```json
{
  "schema_version": "zc07.dataset.v1",
  "documents": [
    {
      "doc_id": "DOC-EXAMPLE-001",
      "split": "development",
      "document_type": "budget",
      "organization_type": "department",
      "source_type": "native",
      "mixed": false,
      "replay_path": "outputs/zc07_replay/DOC-EXAMPLE-001.json"
    }
  ]
}
```

`split` 只能为 `development` 或 `blind`；`document_type` 为 `budget` 或 `final`；`organization_type` 为 `department` 或 `unit`；`source_type` 为 `native` 或 `scanned`。每个集合至少 32 份，八个分层每层至少 4 份；盲测需至少 100 个按 `truth_id` 去重的真实缺陷组。原件 SHA 跨集合重复会报错。`mixed` 用于另行标记混合文种/版式材料，不能替代分层配额。

### 扫描认证的正式装配

扫描页没有可核实文本层时，只有独立人工认证可以使对应引用成为 `verified`；没有认证的引用保持 `unverified`。认证逐条绑定原件、物理页、格身份、引文、框、模型及原始预测，不会因同页另一格的相同金额通过认证而自动通过。

将原件放在 `corpus/<doc_id>/original.pdf`，认证清单放在该目录内，例如 `attestations/scan.json`；复核附件路径相对于认证清单所在目录，例如 `attestations/reviews/page-08.record`。清单路径与附件路径都必须留在各自目录内，不接受越界路径。附件是实际独立复核记录，应包含原件与区域身份、审阅结论、复核人及分歧处理记录。由真实人员签认并冻结，不能将 OCR 输出或本系统生成的候选包当作人工签认。

先按 `scan_attestations.template.json` 填写每个独立认证区域及复核附件 SHA-256，再对最终清单文件计算 SHA-256，写入对应 `golden.json` 的两个字段：

```json
{
  "scan_attestations_file": "attestations/scan.json",
  "scan_attestations_sha256": "<最终清单文件的64位SHA-256>"
}
```

`scan_attestations_file` 是相对于 `corpus/<doc_id>/` 的文件路径。缺字段、文件不存在、SHA不符或复核附件不匹配都不会通过认证。原生材料不需扫描认证时保留两个字段为 null。空模板保持未完成，不能计入认证率。

部署端须另外配置 `OCR_EVIDENCE_ATTESTATIONS_PATH` 为实际外部清单的绝对路径，并将 `OCR_EVIDENCE_ATTESTATIONS_SHA256` 固定为其SHA；容器中还须挂载清单和附件，使相对目录保持一致。正式评测端从各文档的 golden 字段加载对应冻结清单，不以部署环境变量代替。这两端应使用相同、实际签认的认证版本；只配置一端不代表另一端已经装配。模型或原始预测版本改变后，旧认证不自动沿用。

## 真实 E2E 证据清单

证据 JSON 记录四条完整链路的实际执行结果，不能只填浏览器模拟状态。每个 `artifact_path` 指向日志/追踪/测试产物，并填写其 SHA-256。所有场景都必须确认真实 API、Worker 消费、PostgreSQL、原件证据和下载成功；扫描预算及混合决算还需 OCR；混合决算还需证明人工校正后重新审校。

```json
{
  "schema_version": "zc07.e2e-evidence.v1",
  "scenarios": {
    "native_budget": {},
    "native_final_known_issue": {},
    "scanned_budget": {},
    "mixed_final_manual_correction": {}
  }
}
```

场景对象须包含 `status: "passed"`、`run_id`、`doc_id`、`job_id`、场景对应的 `document_type` / `source_type` / `mixed`、API/Worker 版本、隔离 PostgreSQL 标识、原件 SHA-256、导出 SHA-256、非空 `reviewed_by`、布尔字段 `api`、`worker_consumed`、`postgres`、`original_evidence`、`downloads_succeeded`，以及 `artifact_path` 与 `artifact_sha256`。含已知缺陷的原生决算须记录 `known_issue_truth_id` 和 `known_issue_detected: true`。扫描场景补 `ocr` 和 OCR 模型 SHA-256；混合决算补 `ocr`、`manual_correction`、`reanalyzed_after_correction`、`correction_id`、`reanalysis_status: "completed"`，并证明校正前后分析版本不同。只追加校正记录、但生产检查没有消费校正并生成新分析版本，不满足此条件。不完整或哈希不一致均视为未通过。

## 指标与门禁解释

TP/FP/FN 和 precision/recall 复用 `scripts/evaluate_golden_corpus.py` 的规则、页码、证据重叠和真值组匹配口径。发布门槛只使用独立盲测集；开发集单独报告，不可混入盲测指标。报告分别列出预算/决算、部门/单位、原生/扫描的盲测统计，并给出描述性 Wilson 95% 区间。页面级准确率仅作为页码代理，不能声称达到 bbox 精确定位门槛。人工复核候选率、重复报警率、证据真实性、必查完成率、逐项回执覆盖、导出一致性、可重复性在现有评测产物中缺少完整标准真值时保持“不可计算”。

门槛沿任务包设为正式问题 precision ≥98%、真实问题 recall ≥95%、高/重大问题零漏报；同时要求真实 E2E 及其余发布门禁均通过。任一缺项不会用 0 样本填成 100%，报告退出码为 2。报告记录代码 revision、清单/回放/端到端产物哈希、每项 gate、运行时间和退出码。

真值组身份优先采用 `truth_group_id`，其次原样 `truth_id`；`annotation_id` 独立标识证据标注。配额与评测共享 `canonical_truth_group`，只兼容完整的 T4a/T4b 等 `T<数字><单个小写字母>` 历史简写，不剥离任意英文尾缀。DOC-001-income 与 DOC-001-expense 是两个组。新材料显式提供 truth_group_id；不得根据系统输出调整冻结真值组。

### 正式回放字段约定

逐文档 `replay_path` 必须包含被测模式对象；当前CLI接受 `legacy` 或 `structured`，不接受 `dual`。选择与实际回放匹配的模式。要计算证据真实性、回执覆盖、精确定位、重复运行和导出一致性，回放还必须包含相应原始字段；缺字段会保持 `not_computable` 或计为门禁失败，不从当前运行结果反推真值。

- **证据真实性**：每条正式 finding 都必须有 `evidence_verification.status`，且 `evidence` 中的每条引用须包含原件 SHA-256 `file_hash`、物理页 `physical_page`、`source_cell_id` 或 `source_block_id`、原文 `quote`、按 `SHA1(file_hash|physical_page|source_id|quote)[:16]` 派生的 `evidence_id`，以及 `verification_status: "verified"`。评测器会再次打开 `corpus/<doc_id>/*.pdf` 校验哈希、页码和文本引文；精确框还须在 bbox 区域内命中。扫描件无可核实文本时须通过上述独立认证，否则保持未核验；同一问题中只要有一条未认证的OCR引用，整体不能算verified。
- **逐项回执**：每份政府预算/决算文档的 `golden.applicable_sub_checks` 都须提供非空、合法、不重复的完整冻结分母。优先使用 `{ "rule_id": "...", "sub_check_id": "..." }` 对象；字符串建议使用 `"rule_id::sub_check_id"`，兼容旧式 `"rule_id:sub_check_id"` 时仅第一个冒号作分隔，保留 sub-check 内部冒号。裸 sub-check ID、空/无效关系、重复关系以及任一文档的空清单都会使完成率不可计算，不会根据实际回执猜分母。每个回执应记录 `status`；未完成项还须记录 `incomplete_reason`。`formula`、`operand_fact_ids` 单独报告为诊断覆盖。
- **精确定位**：仅 `golden.labels` 中 `defect` 标签的真值定位区域进入正式分母；每个独立证据标注的区域分别计数，因此同一缺陷组可以对应多个定位区域。缺陷组召回则按 canonical 组身份去重，二者分母不同。`acceptable`、`manual_review`、`rounding_hint` 不进入正式错误定位分母。finding 必须通过原件认证并达到 `location_level: "exact_cell"` 或 `"exact_span"`，且 bbox 在同一物理页覆盖真值区域至少 50%、面积不超过真值框的 4 倍。只有页码或未认证 bbox 不算精确命中。
- **重复运行**：主回放和 `repeat_replay_path` 都须携带完全一致的 `repeatability_basis`，其中 `source_sha256`、`configuration_fingerprint`、`version_fingerprint` 非空；原件哈希须等于对应 golden。采用 [回放模板](acceptance_templates/replay.template.json)，各回放顶层必须记录实际非空 run_id、带时区 executed_at，两次运行身份和时间均须不同。拒绝同一文件/软链接/硬链接以及同一 run_id 的复制产物；独立运行生成相同业务内容仍可比较。比较 finding、位置、事实/证据 ID、人工决定、回执和检查结论；有生产 meta.fact_context 时还比较其稳定原件/事实值版本token/识别状态和事实计数/覆盖层计数，以及 fact_overlay_applied。parse_run_uid 可含运行UUID，故不因该运行身份变化判业务不一致；事实版本token按身份、值、识别状态计算。两个旧格式均无摘要仍兼容，一个提供一个缺失则不一致。无可信同源同配置同版本基线时不可计算。
- **导出一致性**：清单中的 `export_paths` 各提供同一 `analysis_revision` 的 JSON、CSV、DOCX 和 PDF。JSON 使用 `review_report.schema_version: 2`，并含 `issues`、`tips`、`human_decisions`、`manual_review`、`check_receipts`、`conclusion`；CSV 必须有对应记录类型和身份、位置、决定、回执、结论字段。四种导出都须带有 `REVIEW_REPORT_SHA256`，其值是 canonical `review_report` 的稳定 SHA-256；评测器会重算 JSON 指纹，检查 CSV 摘要行及 DOCX/PDF 正文中的指纹一致，并继续比较 JSON/CSV 业务语义。缺任一格式、指纹或语义字段均不可计算/不通过。
