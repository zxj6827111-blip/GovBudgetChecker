# 单条复核详情加载优化验收

## 结论

详情页确有独立于清单的性能瓶颈：首次任务加载由 effect 和轮询启动重复触发；工作流读取遍历全部任务，并为每条决定重复读取完整详情；结构化侧车与 PDF 预览的鉴权也加载了完整详情。现已针对这些读取路径优化，未改变证据核验、问题分类和完成复核门禁。

## 修改

- 详情首次读取统一由轮询控制器触发，任务详情、结构化侧车、工作流和复核上下文并行读取。同一资源的在途请求合并，响应结束即释放，复核状态不作持久缓存。
- 工作台读取 `/api/workflow?job_id=<当前任务>`，前端代理明确转发该参数，后端先鉴权再读取当前任务的记录；无决定的任务也不能跳过鉴权。原有无参数接口兼容保留。
- 全量工作流按任务复用详情与决定投影。移除 `setdefault` 默认表达式每次执行的重复计算，保留原有决定版本和问题指纹匹配。
- 结构化侧车、原 PDF 与预览只做任务归属鉴权；完整详情继续进行证据定位和报告重建。耗时的完整详情和 PNG 渲染移入线程池。
- 写动作成功后取消旧读取，通过请求序号拒绝旧结果覆盖新状态，再重新读取服务端状态。完成、重开之后不再连续读取两次生命周期。
- 详情请求限制等待时间，读取失败提供重新加载入口；未获取到详情时保留重试能力。

## 性能与内容一致性

在独立诊断进程中，用当前真实工作流数据运行修改前、后的只读函数。禁止触发旧忽略文件迁移，不提交复核写动作，不输出凭据或问题明细。

| 读取流程 | 耗时 | 完整详情读取次数 |
| --- | ---: | ---: |
| 修改前全量工作流 | 5.61 秒 | 50 |
| 修改后兼容全量工作流 | 0.24 秒 | 3 |
| 当前任务无人工决定 | 0.014 秒 | 0 |
| 当前任务已有人工决定，3 个样本 | 0.044～0.118 秒 | 每次 1 |

全量返回的 25 条工作流记录内容完全一致，JSON 的 SHA-256 相同；四个当前任务查询均与旧全量响应按任务过滤的内容完全一致。这里统计的是工作流读取步骤，不能把它当作整个页面的加载时间。

对一份 40 页材料的完整详情单独测量，未预热约 1.06 秒，后续约 0.10 秒。该步骤仍保留必要的原文证据核验，首次 PDF 解析仍有成本。

## 验证

- 170 项后端相关测试通过：包括当前任务范围、每任务一次投影、跨版本忽略不继承、预览鉴权、组织权限、复核生命周期与写接口认证。
- 39 项不同浏览器用例通过：包括首次每种资源仅一次、并行加载、失败重试、确认/忽略/备注、人工补核、完成/重开、换版本/重分析、来源分类与定位、清单返回。新测试首次出现的失败是定位到不存在的测试锚点，修正为真实 PDF 图片锚点后通过。
- 请求合并与取消的单元检查、复核问题集合跨语言契约、适配器、已知回归和轮询检查通过。
- TypeScript、ESLint、Ruff 和隔离目录中的 Next 生产构建通过；正在运行的开发服务缓存未被构建清除。
- 本地 `/health` 与 `/ready` 均为 200。

真实已登录页面无接口拦截地打开两份材料，并验证 PDF 翻页到第 2 页、规则证据跳到第 8 页、AI 证据跳到第 29 页。两类证据定位框正常显示，图片加载成功，材料预览仍要求显式开始复核，完成按钮仍受门禁限制。没有提交任何真实问题判定、开始或完成复核。
