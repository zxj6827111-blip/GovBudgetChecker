# 0. 本次增补的由来

V2 的技术路线成立，本次增补不改变技术方案，只调整三件事：

1. 交付顺序。V2 全部按「生产级审校系统」排期，最有对外价值的能力被排到 20 周之后。本文增加一条演示支线，与 Phase 0 / Phase 1A 并行。
2. 交付形态。明确对外前端与对内后台是两个界面、一套后端，并分别定义验收标准。
3. 模型部署路径与成本。V2 默认了「本地推理节点 + 2 万元硬件」，本文把它降级为条件触发选项，默认路径改为云 API 调用。

另有若干因业务范围澄清而失效或需要改写的条目，集中在第 5 章修订清单。

## 0.1 方案定稿

以下为经本次增补确定的技术路线，后续各章均服务于此：

1. 职责分层：确定性代码负责数值与结构类检查（合计、比例复算、跨表勾稽、缺表、单位换算、年份一致性）；SKILL 加大模型负责语义类检查（说明完整性、增减原因、方向矛盾、口径混用、模板残留、文种误写、章节间冲突）。
2. 两路输出合并后统一经过证据校验，无法反查证据的候选不进入正式 findings。
3. 数值结论一律由系统复算生成 `verified_metrics`，模型主张保留为 `claimed_metrics`，正式报告只使用前者。
4. 正式报告中的问题必须经人工确认；自动化流程只产出内部初筛报告。
5. 模型走云 API，不做本地化部署，不做微调。
6. SKILL 按输入需求拆分为四组并行调用，存放于 `config/prompt_registry/`，由内容哈希管理版本，变更必须附 Golden Corpus 回放对比。
7. 对外前端与对内后台为两个界面、一套后端、同一份分析结果。

## 0.2 本方案的确定性与待确认项

技术路线已定稿。以下四项待确认，其中仅第 1 项可能推翻路线，其余三项只影响参数：

| 待确认项 | 影响 | 若结论不利 |
|---|---|---|
| 材料与调用数据是否允许出域 | 可推翻云 API 路线 | 回退到本地部署，成本升至约 2 万元一次性投入，工期增加硬件采购与验收周期 |
| 真实 token 用量与单份成本 | 影响预算申报数字 | 调整预算额度，不改变路线（量级差异不足以逆转与本地部署的对比） |
| 真实调用延迟与 PDF 解析耗时占比 | 影响并发参数与拆分粒度 | 调整 `AI_AUDIT_MAX_CONCURRENCY` 与分组粒度 |
| 各区 PDF 生成工具链差异与扫描件情形 | 影响解析成功率与模板版本数量 | 增加 `template_version` 与解析策略，不改变架构 |

在第 1 项得到书面确认之前，不得对外承诺部署形态。

# 1. 新增章节 A：演示支线（Demo Track）

## A.1 为什么单列

演示与生产的成败标准不同：

| 维度 | 演示 | 生产 |
|---|---|---|
| 首要指标 | 单份处理时间、证据可点击定位、零编造 | 召回率、可追溯、人工闭环 |
| 材料范围 | 3 至 5 份已知材料，加现场任意一份同类材料 | 四类材料全覆盖 |
| 规则范围 | 4 至 5 类高置信规则 | 全部启用规则 |
| 失败代价 | 一次翻车即失去信任 | 可通过人工复核兜底 |

V2 把两套标准混在同一条排期上，导致证据定位、报告呈现这些演示价值最高的能力被排在最后。

## A.2 范围定义

演示支线只交付以下能力：

- 单份 PDF 上传；
- 点击分析；
- 前台进度显示；
- 问题清单展示；
- 点击任一问题跳转到 PDF 对应页并高亮证据位置；
- 导出一份带截图的问题清单与整改建议。

不在演示支线范围内：批量上传、审核状态流转、误报与漏报标记、训练数据导出、模型对比、政策库检索。

## A.3 启用的规则范围

演示只启用满足「证据可精确定位 + 数值可确定性复算」两个条件的规则，建议首批为：

1. 三公经费合计与分项之和不一致；
2. 基本支出合计与人员经费、公用经费之和不一致；
3. 核心表缺失或标题与内容不符；
4. 文字说明中的金额、比例与对应表格不一致；
5. 收支总表与功能分类表之间的跨表勾稽不成立。

以上五类全部由确定性代码计算，模型不参与数值判断。选择理由是这几类最直观、最容易被现场验证、且一旦成立客户无法反驳。

## A.4 对客户的能力表述口径

统一表述为：

> 数值勾稽由规则引擎精确复算，每一条问题都能反查到原文页码和单元格；AI 负责语义矛盾、说明缺失、口径不一致等规则难以覆盖的部分；所有问题在进入正式报告前由审核人员确认。

禁止对外表述：

- 「AI 全自动审核」；
- 「AI 自动计算表格勾稽关系」；
- 任何隐含 100% 召回或零误报的说法。

理由：承诺全自动等于承诺召回率与精确率，交付不了；而声明「规则算数、AI 管语义、人工终审」既准确，也更经得起现场追问。

## A.5 现场陌生材料的兜底行为

客户必然会现场提供一份未见过的材料。演示支线必须先定义最坏情况：

允许的最坏情况：

- 文种或主体层级无法可靠识别时，显示「需人工确认材料类型」并停止高风险规则；
- 解析质量不达标时，显示 `blocked` 或 `warning` 并说明原因；
- AI 服务不可用时，显示 `degraded`，规则结果照常输出。

不允许出现的情况：

- 静默套错规则集并输出问题清单；
- 输出无法定位到原文的问题；
- 输出任何 mock 或构造数据；
- 规则执行异常被包装成业务问题；
- AI 失败被伪装成「未发现问题」。

因此 `DocumentProfileResolver`、mock 清零、`execution_error` 隔离三项由「P0 之一」提升为「演示阻塞项」。

## A.6 依赖关系

演示支线不新增底层工作，全部依赖 Phase 0 / Phase 1A 已列任务：

| 演示能力 | 依赖 V2 任务 |
|---|---|
| 陌生材料不错路由 | Phase 1A：`DocumentProfileResolver`、消除静默默认 |
| 证据可点击定位 | Phase 1A：canonical parser、稳定 evidence ID |
| 零编造 | Phase 1A：删除全仓 mock 与 fail-open 通路 |
| 异常不伪装成问题 | Phase 3 前置：`execution_error` 独立通道 |
| 数值可复算 | Phase 3：统一数值验证服务（演示期可先用现有 `parse_number` / `tolerant_equal`） |

前端方面无需新建组件，`app/app/components/task-review/` 下的 `PDFHighlighter`、`EvidencePanel`、`ProblemSidebar`、`ReportPreviewModal` 已具备所需能力，演示入口为组装工作。

## A.7 验收清单

- [ ] 5 份演示材料，每份端到端处理时间不超过 5 分钟；
- [ ] 每条输出问题均可点击跳转到正确页码并高亮到目标数字所在区域；
- [ ] 演示材料上零编造问题、零规则异常伪装；
- [ ] 现场投入 3 份未见过的同类材料，全部落在 A.5 的「允许最坏情况」之内；
- [ ] AI 服务人为断开时界面显示 `degraded` 且规则结果仍输出；
- [ ] 导出的问题清单中每条问题都带截图与页码；
- [ ] 演示账号只能看到演示样本集，不出现其他区或其他任务。

## A.8 分两版交付，第一版不接 AI

A.3 列出的五类规则全部由确定性代码实现，不依赖模型。因此演示支线应拆为两版：

演示 v1，不接 AI：上传、分析、五类代码规则、证据跳转、截图、导出。这一版更早、更稳，且现场任何质疑都能用复算过程回应，不存在模型不确定性。

演示 v2，接入 SKILL：在 v1 基础上加入语义类检查（说明缺失、增减原因、方向矛盾、模板残留等），补足「AI 辅助」的能力叙事。

对客户的表述在 v1 阶段即按 A.4 执行，说明数值由规则引擎复算、语义检查正在扩展中，不隐瞒也不夸大。

## A.9 时间预期

演示 v1 在 Phase 1A 完成后 1 周内产出。按 V2 的 Phase 0（2 至 3 周）加 Phase 1A（3 至 4 周）计算，第一个可对外演示版本约在第 6 至 8 周。

演示 v2 依赖 SKILL 拆分与结构化上下文构造器，在 Phase 4 早期产出。

两者均显著早于 V2 里程碑表原定的 13 至 19 周。

# 2. 新增章节 B：交付形态

## B.1 双界面一套后端

| | 对外前端 | 对内后台 |
|---|---|---|
| 使用者 | 客户演示、单部门自助使用 | 内部审核与运维人员 |
| 功能 | 上传、分析、问题清单、证据跳转、导出 | 批量上传、任务队列、自动截图、报告生成、审核闭环、训练数据导出、评测回放 |
| 界面复杂度 | 极简，不出现审核状态字段 | 完整工作台 |
| 数据范围 | 当前任务 | 全部任务与历史 |

要求：

- 两个界面共用同一套 API 与同一份分析结果，不允许对外前端走简化或降级的分析链路；
- 不为追求极简去改造现有工作台，现有 `task-review` 组件保留；
- 对外前端为新增入口页面，不复制业务逻辑。

## B.2 同步与异步边界

- 单份材料：前台同步等待，显示阶段进度，目标 5 分钟内完成；
- 批量材料：提交后即返回，异步队列处理，完成后在列表查看；
- 演示优先演示单份，批量能力以说明和截图呈现，不在现场等待。

现有 job queue 异步模型满足要求，无需架构改动。

## B.3 自动截图

代码基础已存在：`api/routes/files.py` 的 `_render_preview_png` 使用 PyMuPDF 按 `clip_bbox` 裁切渲染 PNG。

新增验收要求：

- 截图区域必须包含被判定的目标数字，不得只截到表头或错行；
- 截图必须带页码标识，便于人工反查原文；
- 截图坐标来源必须是通过校验的 `EvidenceRef`，未通过证据校验的问题不生成截图；
- 截图生成失败时，问题仍可输出，但必须显式标记「无截图」，不得静默省略。

理由：截图进入报告即成为白纸黑字的结论，错误截图的代价高于界面高亮错误。

## B.4 报告分级

报告分两类，在模板与文件名上明确区分：

| 类型 | 内容 | 标识 |
|---|---|---|
| 内部初筛报告 | 全部候选问题，每条标注确认状态 | 文件名前缀与页眉标注「初筛，待人工确认」 |
| 正式报告 | 仅包含已人工确认问题 | 未确认问题不进入正文，可入附录并注明 |

禁止：后台自动跑完直接生成正式报告。自动化只产出初筛报告。

# 3. 新增章节 C：模型部署路径与成本

## C.1 结论

默认路径改为云 API 调用。本地推理节点与 2 万元硬件从「Phase 6 必做」降级为「条件触发选项」。

## C.2 三条路径对比

按业务量每年约 940 份、每份 20 至 30 页、夜间批量处理的前提估算：

| 路径 | 首年成本 | 逐年成本 | 说明 |
|---|---:|---:|---|
| A. 云 API 调用 | 约 1000 至 2000 元 | 约 200 至 500 元 | 含开发期回放；生产期年成本约百元级 |
| B. 云上常驻 GPU 自部署 | 约 1.6 万至 2.5 万元 | 同等 | 按 A10 24GB 实例常驻估算，为空闲时间付费且不形成资产 |
| C. 本地硬件自部署 | 约 2 万元 + 电费约 260 元 | 约 260 元 | 一次性投入，形成资产，但需等待硬件到货与验收 |

路径 B 在本场景下无正当理由：首年成本接近路径 C，而每年重复支出。仅适用于短期临时验证。

按需或竞价 GPU 只适合训练场景（一次性数小时），不适合长期推理。

## C.3 路径 A 的成本构成

以夜间批处理落在空闲时段、关闭思考模式为前提，单份材料估算：

- 固定前缀（规则、口径、少量示例，约 20K tokens）：命中上下文缓存后成本可忽略；
- 文档内容多轮调用（约 80K tokens，缓存未命中）；
- 输出（约 5K tokens）。

单份成本约 0.15 元。据此：

- 生产期：940 份/年，约 140 元；
- 开发期回放：种子集与 Golden Corpus 反复回放，约 400 至 800 元；
- 首年合计给到 2 倍余量，约 2000 元以内。

## C.4 成本控制的两条工程约束

以下两条直接决定成本量级，必须在实现时固化：

1. 批量审校必须使用非思考模式。输出单价显著高于输入，推理过程 token 会成倍抬高成本。
2. Prompt 必须固定前缀在前、文档内容在后，使规则与口径说明命中上下文缓存。缓存命中与未命中的输入单价相差约 30 倍，940 份材料共用同一套前缀，是缓存的理想场景。

## C.5 转向本地部署的触发条件

满足任一条件即重新评估路径 C：

- 主管单位明确规定该类数据不得出域；
- 业务量增长到 API 年成本超过硬件折旧；
- 需要固定模型权重以保证评测基线长期可复现。

第三条对本计划有实质影响：云 API 的模型版本会更新与下线，V2 §12.4 要求的「相同版本重复运行结果一致」在 API 侧只能在一段时间内成立。应对措施不是提前采购硬件，而是：

- `ModelInvocation` 强制记录完整模型版本串；
- 接受厂商换版时评测基线需重建一次，并在版本差异报告中标注基线重建事件。

## C.6 与微调的关系

云 API 模型不提供权重，无法微调；能微调的只有开源权重模型，训练平台（如 ModelScope 模型服务、各云厂商训练服务）训练的对象也只能是开源模型。

因此微调路线的完整成本是「云 GPU 训练费用 + 长期推理算力」，后者又回到路径 B 或 C。按当前业务量，推理算力利用率极低，自建推理在成本上不成立。

V2 §21 的 LoRA 门禁保持 NO-GO，并补充一条前置判断：只有在提示词、长上下文与 RAG 均已用尽仍不达标时，才评估微调。

## C.7 模型选型

### C.7.1 本场景的选型判据

按重要性排序：

1. 上下文长度足以容纳一份材料的全部结构化内容（表格行列 + 章节），否则组一的全局视图检查无法成立；
2. 支持前缀缓存，且缓存命中折扣足够大——本方案单份材料多次调用共享同一前缀，缓存折扣直接决定成本量级；
3. 支持严格 JSON 输出与可关闭的思考模式；
4. 中文财政公文术语理解；
5. 国内可直连，延迟稳定，数据不出境；
6. 单价。

### C.7.2 候选模型与成本对比

单价对比（每百万 tokens，人民币，美元按约 7.1 折算）：

| 项目 | DeepSeek V4 Flash 空闲时段 | DeepSeek V4 Flash 高峰时段 | GLM-5.3-Flash 促销价 | GLM-5.3-Flash 标准价 |
|---|---:|---:|---:|---:|
| 输入（缓存未命中） | 1.50 | 3.00 | 约 0.53 | 约 1.07 |
| 输入（缓存命中） | 0.05 | 0.10 | 约 0.11 | 约 0.21 |
| 输出 | 4.50 | 9.00 | 约 1.78 | 约 3.55 |

GLM-5.3-Flash 促销为标准价五折，促销截止 2026-09-09 24:00（UTC+8），长期预算须按标准价计算。

按 C2.5 的缓存友好 prompt 结构折算单份材料成本（约 20 次调用，段一段二共约 22K tokens 在首次调用后命中缓存，输出合计约 10K tokens）：

| 模型与档位 | 单份成本 | 940 份/年 |
|---|---:|---:|
| GLM-5.3-Flash 促销价 | 约 0.085 元 | 约 80 元 |
| DeepSeek V4 Flash 空闲时段 | 约 0.13 元 | 约 120 元 |
| GLM-5.3-Flash 标准价 | 约 0.17 元 | 约 160 元 |

结论：三者年成本差额在百元以内，在本项目业务量下不构成选型依据。模型选择应依据能力、稳定性与风险，不依据单价。

### C.7.3 关于第三方基准的适用性

公开报道中 GLM-5.3-Flash 优于 DeepSeek V4 Flash 的数据（Terminal-Bench 2.1 84.3 对 82.7、DeepSWE 63.4 对 54.4）均为编程与 agent 类基准，与本项目的中文公文语义判断、长文档结构化理解、严格 JSON 输出三项核心需求没有对应关系，不得作为选型依据。

本项目的模型能力判断只以自有 Golden Corpus 回放结果为准。

### C.7.4 推荐配置

| 角色 | 模型 | 理由 |
|---|---|---|
| 生产主力（当前） | DeepSeek V4 Flash | 1M 上下文；缓存命中价为已核实厂商中最低；空闲时段半价且高峰时段为工作日白天，与夜间批处理互补；已发布约一个月，行为相对稳定；现有 `openai_compat` 通道可直接接入 |
| 并列候选（待评测） | GLM-5.3-Flash | 1M 上下文、原生多模态、支持 Context Caching / Structured Output / Function Calling / 思考模式可关；原生多模态对扫描件材料可能有实质价值；但发布于 2026-08-26，生产稳定性与限流表现未经时间检验，不宜直接作为主力 |
| 开发期调试 | GLM-4.7-Flash 或 GLM-4.5-Flash | 官方定价为免费，用于 SKILL 迭代期的冒烟调试，可将开发期调试成本降为零 |
| 难例升级 | DeepSeek V4 Pro 或 GLM-5.3 | 同厂商内更换模型串即可；仅用于组四跨表语义与低置信候选的二次判断 |
| 质量上限对照 | 一款美国前沿模型 | 仅在 SKILL 改版时于 Golden Corpus 上跑一次，用于区分「模型能力不足」与「SKILL 写得不好」。不进入生产链路 |
| 厂商风险对冲 | 通义千问系列 | 现有 `src/providers/` 已内置 `zhipu`、`doubao`、`openai_compat` 三类适配，切换成本低 |

不推荐将美国模型作为生产主力：数据出境合规、延迟与单价三项均不利，且 V2 §6.1 已确定通用云模型只作外部基准。

### C.7.5 模型评测纳入 Phase 0

在第 4 周的种子集首次完整回放中，同时评测 DeepSeek V4 Flash 与 GLM-5.3-Flash：同一 SKILL 版本、同一结构化输入、同一 Golden Corpus，比较分类别召回率、证据可反查率、JSON 格式合规率、单份延迟与实际 token 用量。以该结果决定生产主力，而非以厂商基准或发布时间决定。

### C.7.6 模型的可替换性要求

模型是可替换组件，不得成为架构依赖：

- 全部调用通过 `openai_compat` 抽象，不在业务代码中出现厂商专有字段；
- 模型串、BASE URL、并发上限、阈值全部配置化；
- `ModelInvocation` 记录完整模型版本串，厂商换版即视为基线重建事件；
- 每季度用同一 Golden Corpus 与同一 SKILL 版本横评一次候选模型，仅在质量或成本出现显著差异时更换；
- 不得基于限时促销价做长期预算或选型决策。

# 3A. 新增章节 C2：SKILL 工程与调用编排

## C2.1 现状：SKILL 已存在，且是当前生产路径

`src/engine/ai/extractor_client.py` 已包含：

- `FULL_REPORT_AUDIT_PROMPT_ID = "full_report_audit_direct"`；
- `FULL_REPORT_AUDIT_PROMPT_INSTRUCTIONS`：8 条约束、容差规则、口径保护、OCR 噪声保护、输出 schema 与示例；
- `full_report_audit_prompt_version()`：由提示词内容哈希派生的版本号。

项目根目录 `AGENTS.md` 是同类产物的另一份实现。

因此本项目不需要论证「是否采用 SKILL」，SKILL 已在运行。需要解决的是它当前的能力上限来源。

## C2.2 当前 SKILL 的能力被输入形态锁死

该 SKILL 第 3 条明确写着：

> 局部窗口限制：不要判断全书缺表、缺章、目录页码整体错误等必须看全书才能确认的问题。

原因是输入为 `AI_AUDIT_WINDOW_CHARS`（默认 12000）字符的文本切窗，模型拿不到全局视图，因此 SKILL 主动放弃了缺表检查——而缺表是业务方最需要的检查项之一。

同理，第 4 条要求模型检查「合计与明细勾稽不一致」，但模型看到的是表格被拼平后的文本，行列关系已丢失。

另外 `MIN_ISSUE_CONFIDENCE` 被格式化进提示词末尾（「低于 0.75 置信度的问题不要输出」），而 `src/services/ai_findings.py` 在转换阶段又按同一阈值过滤一次，构成双重过滤。这是「多份材料 AI findings 为 0」的直接原因之一。

结论：SKILL 替代的是微调，不替代结构化事实层。改写 SKILL 文本不会突破上述限制，改变输入形态才会。

## C2.3 分层判据：哪些写代码，哪些写 SKILL

判据：该检查项的结论能否由一个确定的公式或存在性判断得出。

能，写代码（必须由确定性代码实现）：

- 合计与分项之和；
- 比例、同比、完成率、结构占比复算；
- 跨表勾稽；
- 缺表与空表判定；
- 单位换算与量级校验；
- 年份一致性。

理由：这类结论会被客户当场验算，且只有代码能写回归测试并保证重复运行一致。

不能，写 SKILL：

- 说明是否完整；
- 增减是否写明原因；
- 数字方向与文字方向是否矛盾；
- 前后表述是否自相矛盾；
- 口径混用；
- 模板残留、占位符、重复表述、残句；
- 文种与主体层级误写；
- 章节之间描述冲突。

据此，当前 SKILL 第 4 条中的「同比、占比、完成率复算错误」与「合计与明细勾稽不一致」两项应从 SKILL 中移除，收回给代码实现。

## C2.4 SKILL 拆分方案：按输入需求分组

拆分依据是输入需求，不是问题类型的主观归类。需要相同输入的 SKILL 合并为一次调用，需要不同输入的必须分开。

| 组 | 输入 | 覆盖检查项 | 单份调用次数 |
|---|---|---|---:|
| 组一 全局视图 | 全文档表格清单摘要（表名、页码、行列数、单位） | 缺表、表名与内容不符、目录与正文表数不一致 | 1 |
| 组二 表与说明配对 | 单张表的结构化行列 + 其对应说明章节 | 文字金额与表格不一致、增减原因缺失、口径混用 | 约 9 至 10 |
| 组三 纯文本章节 | 单个说明章节文本 | 模板残留、占位符、重复表述、残句、文种误写、年份冲突 | 约 9 |
| 组四 跨表语义 | 两至三张相关表的摘要 + 相关说明 | 表间描述矛盾、口径解释不一致（数值判断仍归代码） | 少量 |

组一是当前完全无法覆盖的部分，因为文本切窗拿不到全局表格清单。

## C2.5 Prompt 顺序与缓存约束

上下文缓存按前缀匹配。同一份材料的多次调用必须采用以下顺序，否则缓存无法命中：

```text
[段1] 通用系统指令：角色、容差、输出 schema、禁止编造（所有 SKILL 共享，全局固定）
[段2] 本份材料的结构化内容（同一材料的全部调用完全相同）
[段3] 本次调用的具体 SKILL 指令（唯一变化部分，篇幅短）
```

段 1 与段 2 在同一材料的 N 次调用中完全相同，首次调用后即命中缓存，输入单价从缓存未命中价降至命中价（相差约 30 倍）。

实现约束：变化部分必须置于末尾。此顺序与常规「先指令后内容」的写法相反，属于易错点，需在代码中注释说明原因。

## C2.6 速度分析

关键前提：大模型调用的延迟主要由输出 token 数决定（逐 token 解码），输入为并行预填充，且缓存命中后预填充开销进一步下降。因此「调用次数增加」不等于「总耗时成倍增加」。

现状估算：材料提取文本 6000 至 17600 字，按 12000 字符切窗实际只产生 1 至 2 个窗口，并发上限 `AI_AUDIT_MAX_CONCURRENCY` 默认 2，即 1 批完成。单次需在一份提示词内完成 7 类检查，输出较长，单次约 30 至 50 秒。

拆分后估算：约 20 次调用，单次输入短（缓存命中）、输出短（仅一类问题，约 300 至 800 tokens），单次约 10 至 20 秒；并发提升至 8 至 16 时为 2 至 3 批，合计约 30 至 60 秒。

结论：两者处于同一量级，均远低于「单份 5 分钟」的演示目标。单份处理的真实瓶颈是 PDF 解析（`DEFAULT_TABLE_SETTINGS` 对每页依次尝试 lines / lines_strict / text 三种策略），而非模型调用次数。

因此不得以「减少调用次数」为理由牺牲按类别可评测性。需同步调整：`AI_AUDIT_MAX_CONCURRENCY` 默认值从 2 提升，并按厂商并发限制设定上限。

## C2.7 准确率提升的来源与优先级

按预期收益排序，前三项不完成时第四项无意义：

1. 修复解析与字段语义类型（编码列被当金额、数字被当年份、空值与零值混淆）。作用是消除现有误报，属于「减少错的」。
2. 引入结构化输入与全局视图，并把缺表、勾稽、比例复算交由代码实现。作用是覆盖当前完全查不到的检查项，属于「增加对的」。
3. SKILL 按类别拆分、阈值从提示词外移至代码侧按类别配置、输入改为结构化。作用是让语义类问题从接近零覆盖变为可测量、可调优。
4. LoRA 微调。边际收益最小，且需要 1000 条以上可训练样本与 500 条以上 hard negative，当前不具备。

据此明确：SKILL 工程能解决语义类检查的覆盖问题，不能解决数值与结构类检查——后者必须由代码承担。二者相加才构成完整能力，任何一方单独都不足。

## C2.8 SKILL 工程化要求

1. SKILL 从 Python 常量抽出到 `config/prompt_registry/`（V2 §17.2 已列该目录），使规则维护人员可在不改代码、不发版的前提下修改。
2. 每个 SKILL 具备 `skill_id`、`skill_version`、适用问题类别、所需输入类型、置信度阈值、评测集引用。
3. 置信度阈值不得写入提示词文本，改由代码侧按问题类别配置，并通过 Golden Corpus 校准。
4. 每次调用在 `ModelInvocation` 中记录 `skill_id`、`skill_version`、`input_scope`（本次携带的表与章节）。
5. 结果合并去重键须包含 evidence 的 `cell_id` 或 `section_id`，避免组二与组四重复上报同一问题。
6. 单个 SKILL 执行失败必须产生独立的失败状态，结果中标明该类别未完成检查；禁止以空数组表示「未发现问题」。
7. SKILL 内容变更即产生新版本号（现有 `full_report_audit_prompt_version()` 的内容哈希机制可直接复用），变更必须附 Golden Corpus 回放对比结果方可上线。
8. 每个 SKILL 可独立启停与独立回滚，某一类误报过高时禁用该 SKILL 不影响其他类别。

## C2.9 对本地部署与训练的结论

综合 C2.7 与第 3 章：

- 不需要本地化部署。默认走云 API，触发条件见 C.5。
- 不需要训练。SKILL 工程加结构化输入即可覆盖微调的目标收益；微调保持 NO-GO，且排在准确率提升来源的第四位。
- 唯一可能推翻上述结论的因素是数据出域合规要求，属于管理决定，不属于技术选型。
