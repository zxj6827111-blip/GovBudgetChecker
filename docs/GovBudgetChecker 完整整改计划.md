# GovBudgetChecker 完整整改计划

> 文档版本：V1.0  
> 编制日期：2026-07-31  
> 文档状态：待评审  
> 适用项目：GovBudgetChecker  
> 目标：解决 PDF 漏检、结果不可信、操作体验差、状态误报和生产可靠性不足等问题。

---

## 1. 整改结论

当前系统已经具备上传 PDF、解析文档、执行规则、调用 AI、生成审核结果和前端查看结果等基本能力，可以视为一个工程化 MVP。

但从现有真实 PDF 验证结果看，系统尚未形成可信的业务闭环，当前不适合直接用于正式预算审核或生产决策。

### 当前发布判断

**NO-GO：暂不具备生产发布条件。**

主要原因：

1. 系统将“程序没有抛异常”当成任务成功，不能证明文档分析正确。
2. 扫描 PDF 缺少完整 OCR 兜底，部分页面可能根本没有进入审核。
3. 年份识别失败时被默认写成 `2000`，掩盖真实识别失败。
4. 文档类型大量为 `unknown`，导致专用审核规则没有执行。
5. AI 或规则分析失败时可能返回空问题，用户无法区分“没有问题”和“分析失败”。
6. 前端可能将接口异常转换成空数据，形成静默失败。
7. 审核结论缺少稳定的 PDF 页码、原文和位置证据链。
8. 自动化测试以合成文本和表格为主，不能证明真实 PDF 的识别准确率。

## 2. 已发现的基线问题

历史验证文件：

`docs/validation_2026_batch_summary.json`

共包含 118 份文档的验证结果。

| 指标 | 当前结果 | 风险 |
|---|---:|---|
| 标记为处理成功 | 118/118 | 成功状态可信度不足 |
| 年份为 2000 | 118/118 | 年份识别失败被默认值掩盖 |
| 文档类型为 unknown | 118/118 | 专用审核规则可能未运行 |
| review_item_count 为 0 | 118/118 | 疑似系统性漏检 |
| 表格数量少于 9 | 12 份 | 表格提取不完整 |
| 表格数量少于 5 | 3 份 | 严重提取不足 |
| facts_count 为 0 | 3 份 | 文档没有形成可审核事实 |
| 明显组织名称错配 | 至少 13 条 | 机构归属结果不可靠 |
| report_id 异常复用 | 1 个 ID 对应 9 个组织 | 报告标识存在碰撞或生成错误 |

现有自动化测试结果：

- 82 项测试通过。
- 测试主要覆盖合成文本、合成表格及局部逻辑。
- 现有测试不能证明真实 PDF、扫描件、复杂表格和异常文件能够正确处理。

## 3. 问题优先级

### P0：阻止生产发布

| 编号 | 问题 | 影响 |
|---|---|---|
| P0-01 | 扫描 PDF 没有可靠 OCR 兜底 | 页面内容未进入审核 |
| P0-02 | 成功状态只代表没有抛异常 | 用户收到虚假成功结果 |
| P0-03 | 年份识别失败默认返回 2000 | 错误数据被当成正常数据 |
| P0-04 | unknown 类型只执行通用规则 | 大量专用审核项被跳过 |
| P0-05 | AI 失败可以返回空 findings | 分析失败被误认为没有问题 |
| P0-06 | 前端隐藏接口异常 | 用户看不到真实失败原因 |
| P0-07 | 结果没有完整证据链 | 审核结论无法复核 |
| P0-08 | 缺少真实 PDF Golden Corpus | 无法衡量漏检率和准确率 |
| P0-09 | report_id 可能重复 | 报告串数据、覆盖或归属错误 |

### P1：影响用户效率和系统可信度

| 编号 | 问题 | 影响 |
|---|---|---|
| P1-01 | 上传、处理、复核流程割裂 | 操作步骤多且状态不清晰 |
| P1-02 | 缺少处理阶段进度 | 用户不知道系统正在做什么 |
| P1-03 | 无法方便修正年份、类型、组织 | 识别错误后只能重新上传 |
| P1-04 | 详情加载数量可能固定为 30 | 历史任务或结果无法完整访问 |
| P1-05 | unknown 类型被适配为预算类型 | 前端展示与后端真实结果不一致 |
| P1-06 | 缺少批量重试和批量复核 | 大批量文件处理效率低 |
| P1-07 | 缺少搜索、筛选、排序和状态统计 | 用户难以定位重点任务 |
| P1-08 | 错误信息缺少解决建议 | 用户无法自行恢复任务 |

### P2：影响长期维护和生产运营

| 编号 | 问题 | 影响 |
|---|---|---|
| P2-01 | 缺少阶段级指标和监控 | 无法快速定位漏检发生在哪一步 |
| P2-02 | 缺少规则版本和模型版本记录 | 历史结果不可复现 |
| P2-03 | 缺少数据迁移与重分析机制 | 修复后旧数据仍然错误 |
| P2-04 | 缺少性能基线和容量测试 | 大文件和并发任务风险未知 |
| P2-05 | PDF 安全隔离不足 | 恶意或异常 PDF 可能影响服务 |
| P2-06 | 缺少正式发布门禁 | 测试通过不等于业务质量达标 |

## 4. 整改目标

### 4.1 业务目标

1. 系统能够明确区分：
   - 没有发现问题；
   - 文档无法完整分析；
   - 文档需要人工复核；
   - 分析过程失败。

2. 每一个审核问题都能够定位到：
   - PDF 文件；
   - 页码；
   - 原文或表格；
   - 规则编号；
   - 判断原因；
   - 实际值和期望值。

3. 用户可以在统一工作台完成：
   - 上传；
   - 查看进度；
   - 修正元数据；
   - 查看审核问题；
   - 跳转 PDF 证据；
   - 重试；
   - 导出报告。

### 4.2 质量目标

以下指标必须基于人工标注的真实 PDF Golden Corpus 测量。

| 指标 | 发布目标 |
|---|---:|
| 可解析页面覆盖率 | ≥ 99% |
| 扫描页面 OCR 成功率 | ≥ 98% |
| 年份识别准确率 | ≥ 98% |
| 文档类型识别准确率 | ≥ 95% |
| 组织名称识别准确率 | ≥ 98% |
| P0/P1 审核问题召回率 | ≥ 95% |
| 审核问题精确率 | ≥ 90% |
| 审核结论证据完整率 | 100% |
| 静默失败数量 | 0 |
| report_id 唯一性 | 100% |
| 关键流程 E2E 通过率 | 100% |
| 线上未捕获错误率 | 接近 0 |

### 4.3 用户体验目标

1. 上传后立即显示文件校验结果。
2. 每个任务显示当前处理阶段、进度和预计状态。
3. 用户可以在三次操作内从问题列表跳转到 PDF 证据页。
4. 分析失败时必须显示失败阶段、原因和恢复操作。
5. 不使用空列表掩盖接口异常。
6. 支持按状态、年份、组织、文档类型和问题级别筛选。
7. 支持批量上传、批量重试、批量导出和批量复核。

## 5. 整改总体阶段

本次整改建议拆分为八个阶段。

| 阶段 | 名称 | 建议周期 | 主要目标 |
|---|---|---:|---|
| Phase 0 | 基线冻结与 Golden Corpus | 1～2 周 | 建立真实质量基线 |
| Phase 1 | 状态模型与质量门禁 | 1～2 周 | 消除虚假成功和静默失败 |
| Phase 2 | PDF、OCR 与表格提取 | 2～3 周 | 确保文档内容完整进入系统 |
| Phase 3 | 年份、类型与组织识别 | 1～2 周 | 修复关键元数据识别 |
| Phase 4 | 规则、AI 与证据链 | 2～3 周 | 提升问题发现能力和可解释性 |
| Phase 5 | 用户工作流与前端重构 | 2～3 周 | 改善操作效率和用户体验 |
| Phase 6 | 可靠性、监控与生产化 | 1～2 周 | 建立运行保障能力 |
| Phase 7 | 全量回放、迁移与发布 | 1～2 周 | 完成历史修复和正式验收 |

标准团队预计总周期：**10～14 周**。

若只有 3～4 名开发及测试人员，预计需要 **14～20 周**。

排期应在 Phase 0 完成后，根据真实 PDF 的复杂度重新校准。

## 6.1 目标

建立一套人工确认过的真实 PDF 数据集，用于计算系统的漏检率、准确率和回归结果。

## 6.2 工作任务

- [ ] 冻结当前代码版本、规则版本、模型配置和验证数据。
- [ ] 保存现有 118 份文档处理结果，作为整改前基线。
- [ ] 建立不少于 150 份真实 PDF 的 Golden Corpus。
- [ ] 覆盖文本 PDF、扫描 PDF、混合 PDF、旋转页面和复杂表格。
- [ ] 覆盖不同年份、组织、预算类型和文档模板。
- [ ] 每份文档由人工标注年份、类型、组织和问题清单。
- [ ] 每个问题标注页码、原文、规则和严重级别。
- [ ] 至少安排两人交叉复核高风险样本。
- [ ] 建立机器可读取的 JSON 标注格式。
- [ ] 编写自动回放及指标统计脚本。
- [ ] 记录每个失败样本发生在哪个处理阶段。
- [ ] 建立整改前后的质量对比报告模板。

## 6.3 样本类型

Golden Corpus 至少覆盖：

- 正常文本型 PDF；

- 带页眉、页脚和水印的 PDF；
- 多栏排版 PDF；
- 跨页表格；

- 多个年份同时出现的文档；
- 组织简称、别名和上级单位混合出现的文档；
- 无问题文档；
- 已知问题文档；
- 加密 PDF；
- 损坏或不完整 PDF；
- 超大页数 PDF。

- [ ] 每个样本都有人工确认结果。
- [ ] 高风险问题完成双人复核。

# 7. Phase 1：状态模型与质量门禁

## 7.1 目标

修复“没有抛异常就算成功”的设计，确保系统状态真实反映业务处理结果。

## 7.2 建议状态模型

任务状态建议调整为：

| 状态 | 含义 |
|---|---|
| queued | 已进入队列 |
| validating | 正在校验文件 |
| parsing | 正在解析 PDF |
| ocr_processing | 正在执行 OCR |
| extracting | 正在提取文本、表格和事实 |
| classifying | 正在识别年份、类型和组织 |
| analyzing | 正在执行规则及 AI 分析 |
| quality_check | 正在执行质量门禁 |
| review_required | 自动分析不完整，需要人工复核 |
| completed | 分析完整并通过质量门禁 |
| failed | 无法继续处理 |
| cancelled | 任务被取消 |

质量状态单独保存：

- `pass`
- `warning`
- `fail`

分析结论单独保存：

- `findings_detected`
- `no_findings`
- `incomplete`
- `analysis_error`

## 7.3 工作任务

- [ ] 重构 `api/main.py` 中任务最终状态判定逻辑。
- [ ] 禁止仅根据“是否抛异常”设置 `completed`。
- [ ] 建立统一的阶段执行结果结构。
- [ ] 保存每个阶段的开始时间、结束时间和错误信息。
- [ ] 保存页面覆盖率、OCR 覆盖率和表格提取数量。
- [ ] 保存元数据识别置信度。
- [ ] 保存实际执行的规则列表。
- [ ] 明确区分“没有问题”和“分析没有完成”。
- [ ] AI 调用失败时禁止返回伪装成正常结果的空 findings。
- [ ] 前端禁止将接口异常转换成正常空数组。
- [ ] 添加 `review_required` 状态。
- [ ] 添加任务级质量门禁。
- [ ] 修复 report_id 生成及唯一性约束。
- [ ] 数据库增加唯一索引和冲突处理。
- [ ] 增加任务重试次数和最后一次错误字段。
- [ ] 为旧状态提供兼容迁移。

## 7.4 建议质量门禁

任务只有满足以下条件才能进入 `completed`：

- PDF 文件校验通过；
- 总页数大于 0；
- 所有页面都有文本或 OCR 处理结果；
- 页面处理覆盖率达到阈值；
- 关键元数据已识别，或者由用户确认；
- 文档类型对应的规则已经执行；
- 规则引擎没有发生未处理错误；
- AI 被配置为必需时，AI 分析必须成功；
- 每个问题都有证据；
- 结果通过 schema 校验；
- report_id 唯一；
- 不存在未处理的 P0 质量告警。

无法满足完整条件但仍有部分有效结果时，应进入 `review_required`，而不是 `completed`。

## 7.5 重点影响文件

- `api/main.py`
- `src/services/analyze_dual.py`
- `src/engine/pipeline.py`
- 任务模型及数据库迁移文件
- API response schema
- 前端任务状态适配器
- 相关单元测试和集成测试

## 7.6 验收标准

- [ ] OCR 失败不会显示为正常完成。
- [ ] AI 失败不会显示为“没有问题”。
- [ ] unknown 类型不会被自动伪装成预算文档。
- [ ] 接口异常不会显示为空结果。
- [ ] 每个任务可以查看阶段级处理记录。
- [ ] report_id 不再发生重复。
- [ ] 状态迁移具有自动化测试。
- [ ] 旧任务可以正常查看或明确标记为历史结果。

# 8. Phase 2：PDF、OCR 与表格提取

## 8.1 目标

确保每一页 PDF 都得到处理，并能够判断提取是否完整。

## 8.2 建议处理链路

1. 文件安全校验；
2. PDF 基础结构检查；
3. 原生文本提取；
4. 页面文本质量评估；
5. 自动识别扫描页面；
6. 对扫描或低质量页面执行 OCR；
7. 合并原生文本和 OCR 文本；
8. 表格检测与提取；
9. 页面布局及坐标保存；
10. 提取质量评分；
11. 不达标时进入人工复核。

## 8.3 工作任务

- [ ] 为 PDF 处理建立独立服务层。
- [ ] 保留 `pdfplumber` 作为原生文本提取能力。
- [ ] 添加页面级 OCR fallback。
- [ ] 支持混合 PDF，仅对需要的页面执行 OCR。
- [ ] 检测空白文本、乱码、字符异常和低文本密度。
- [ ] 支持页面旋转纠正。
- [ ] 保存 OCR 引擎、版本、语言和置信度。
- [ ] 保存每个文本块的页码和坐标。
- [ ] 保存每个表格的页码和区域。
- [ ] 改进跨页表格识别。
- [ ] 改进合并单元格、无边框表格和多行表头处理。
- [ ] 对原始文本、OCR 文本和清洗文本分别留档。
- [ ] 增加超时、内存和最大页数限制。
- [ ] 对损坏和加密 PDF 返回明确错误。
- [ ] 对恶意 PDF 使用隔离进程或受限执行环境。
- [ ] 为 OCR 引擎设计可替换适配层。
- [ ] 建立提取质量评分模型。
- [ ] 低于质量阈值时禁止自动完成任务。

## 8.4 页面级数据结构

每个页面建议保存：

- `page_number`

- `extraction_method`
- `native_text`

- `normalized_text`
- `text_blocks`
- `tables`
- `ocr_confidence`
- `text_coverage`
- `quality_score`

## 8.5 重点影响文件

- `api/main.py`
- PDF 解析服务
- OCR adapter
- 表格提取服务
- 文档结构模型
- 文件存储服务
- PDF 提取相关测试

## 8.6 验收标准

- [ ] 文本 PDF 可以稳定提取。
- [ ] 扫描 PDF 自动触发 OCR。
- [ ] 混合 PDF 只对必要页面执行 OCR。
- [ ] 旋转页面能够被识别和纠正。
- [ ] 每页都有明确处理结果。
- [ ] 页面覆盖率可以自动计算。
- [ ] 表格数量和人工标注结果达到目标。
- [ ] OCR 或表格提取失败会进入 `review_required`。
- [ ] 超大、加密和损坏 PDF 有明确错误提示。
- [ ] Golden Corpus 页面覆盖率达到发布指标。

- `task_implementer`：执行范围明确的最小代码修改；
- `test_verifier`：独立运行测试并核对结果；
- `risk_reviewer`：对阶段改动进行第二视角审查；
- `browser_debugger`：复现真实页面操作和接口问题；
- `docs_researcher`：核对 OCR、PDF、框架和 SDK 官方行为。

不得让多个可写 Agent 同时修改同一批文件。

# 17. 依赖关系

建议严格按照以下顺序实施：

1. 先建立 Golden Corpus；
2. 再修复状态模型和质量门禁；
3. 再修复 PDF、OCR 和表格提取；
4. 再修复年份、类型和组织识别；
5. 再完善规则、AI 和证据链；
6. 后端状态稳定后重构前端；
7. 完成监控、可靠性和安全建设；
8. 最后进行历史迁移、全量回放和发布。

不能先只改前端。

如果后端仍然返回虚假成功、错误元数据和不完整结果，即使页面体验改善，也无法解决系统核心可信度问题。

# 18. 回滚原则

## 18.1 代码回滚

- 每个 Phase 单独建立可回滚版本。
- 数据库迁移必须提供向前修复方案或明确回滚脚本。
- 规则版本和模型配置不能只保留最新版本。
- 生产发布使用版本化制品，不在服务器上直接修改代码。

## 18.2 数据回滚

- 历史报告不直接覆盖。
- 新分析结果使用新版本记录。
- 保存旧报告和新报告的关联关系。
- report_id 修复必须保存旧 ID 映射。
- 用户人工复核记录不得因重新分析丢失。

## 18.3 发布回滚触发条件

出现以下任一情况应立即停止或回滚：

- 页面覆盖率明显下降；
- unknown 比例异常升高；
- findings 大量异常归零；
- report_id 冲突；
- 报告串联到其他组织；
- AI 或 OCR 连续不可用；
- 数据库迁移导致旧报告无法访问；
- P0/P1 漏检率超过发布阈值；
- 用户无法访问或复核已完成报告。

## 26. 总结

本次整改不能只作为一次前端美化或局部 PDF 解析修复。

系统当前最关键的问题是：

1. 无法证明 PDF 被完整读取；
2. 无法证明适用审核规则被完整执行；
3. 无法区分没有问题和分析失败；
4. 无法通过证据链复核审核结论；
5. 系统状态与真实业务质量不一致。

因此，整改必须按照“真实数据基线、状态模型、内容提取、元数据识别、审核能力、证据链、用户工作流、生产保障”的顺序推进。

在 Golden Corpus 指标、关键用户流程和生产门禁全部通过之前，系统应继续保持 **NO-GO** 状态，不应用于替代正式人工审核。
