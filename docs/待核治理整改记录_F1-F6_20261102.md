## 3. 逐项整改

### F1 缺失操作数页码

- 问题：`native_table_arithmetic.select_diagnostic` 用整表首个事实的页码，可能把第 7 页其他行的位置安到第 8 页的目标行。
- 修改：`fact_context.matching_row_page` 只接受与请求科目编码（优先）或名称匹配的事实，并且要求其原格证据同时带 `source_cell_id` 与 `physical_page`；页码集合必须唯一，否则返回 `null`。`fact_page` 对单个事实同样要求唯一且可证明的页码。
- 同步覆盖：支出/基本支出表中按事实逐行生成的缺失规格改用 `fact_page(fact)`；未找到合计行时不再借用整表首页，直接 `page=null`；`native_summary_checks` 的名称匹配缺失规格改用 `matching_row_page`。
- 证据：`tests/test_dh02_diagnostics.py::test_missing_operand_page_uses_same_row_evidence_only`；复核方合成复现 `missing_page` 由 `reproduced=true` 变为 `false`（8→8，非 7）；`<EVID>/diagnostic_reproductions_fix.json`。

### F2 规则不依赖的 org_scope 阻断

- 问题：`operand_rejection_diagnosis` 无条件把 `org_scope_pending` 生成为上游阻断。
- 修改：读取规则执行上下文 `ACTIVE_IDENTITY`，只有当前规则实际声明 `org_scope` 时才生成该阻断；`org_scope` 实参分支同样受该维度约束。准入判定与规则状态不变。
- 证据：`tests/test_dh02_diagnostics.py::test_org_scope_blocker_only_when_rule_requires_that_dimension`；复核方合成复现 `irrelevant_scope` 变为 `false`，`next_action` 回到 `tech_fix`；160 份真实输出扫描 22,349 个阻断项，0 个维度越界、0 个规则未声明 `org_scope` 的阻断（`<EVID>/f2_f3_dimension_scan.json`）。

### F3 行/列原因被泛化

- 问题：`missing_subject_code` 与 `cross_page_width_drift` 被统一输出为 `cell_low_confidence`。
- 修改：识别状态不可用时优先消费已有类型化来源：`row_identity_status=missing_subject_code` → `row_code_missing`（维度 row）；`column_identity_status=cross_page_width_drift` → `column_width_drift`（维度 column）；`arithmetic_conflict` → `column_identity_unconfirmed`（维度 column）。只有来源没有具体类型时才退回 `cell_low_confidence`。拒绝状态与 `operand_missing` 保留。
- 证据：`tests/test_dh02_diagnostics.py::test_typed_identity_status_reports_row_and_column_reasons`；复核方合成复现 `column_drift`/`row_code_missing` 均变为 `false`；真实输出出现 `row_code_missing` 28 条、`column_identity_unconfirmed` 4 条，所有阻断维度均在冻结维度表内。

### F4 前端同源提示仍读旧 detail

- 问题：`buildSameSource` 仍用 `/找不到同名科目/` 匹配 `detail`，56 份冻结回归材料在文案切换后丢失 V33-227 提示。
- 修改：新结果优先读冻结结构化依据：`reason_codes` 含 `subject_name_unlocated`，或含 `text_binding_failed` 且 `legacy_coverage_terms` 非空；只有 `reason_codes` 缺失或为 `null` 时才回退旧 `detail` 正则。`[]` 是合法新结果，不回退。
- 证据：`app/tests/obligationGuidance.test.ts`；对复核方列出的 56 份材料逐份调用新前端逻辑，56/56 保留 V33-227 提示；基线旧 detail 触发的 56 份在新结果中同样 56/56 保留（`<EVID>/f4_same_source_verification.json`）。

### F5 前端丢失具体诊断信息

- 问题：文字操作数不显示角色/页码，候选只显示数量，`rule_no_reason` 遮住保留的业务说明。
- 修改：`describeObligationDiagnosis` 对表/文字操作数分别展示表名、页码、角色、行、列，对候选展示具体位置与值；`rule_no_reason` 时从 `detail` 的“规则说明：”标签段提取并展示业务说明，不对 `detail` 做语义匹配。
- 证据：`app/tests/obligationGuidance.test.ts`、`app/tests/reviewObligationAdapters.test.ts`；Playwright 实际卡片与默认备注断言：角色“住房公积金决算金额”、第 12 页、候选「10.00」、规则说明均可见，默认备注与卡片同源（`<EVID>/logs/e2e_obligation_card_fix.log`）。

### F6 “已取到”统计口径

- 问题：旧文案累加未完成子回执的 `operand_fact_ids`，不去重；158 条在未完成子检查无操作数时误写成整个义务“没有可用操作数”。
- 修改：`render_obligation_detail` 同时接收诊断子回执与全义务关联回执，按不同事实 ID 去重，并同时给出引用次数；文案明确区分“本次未完成子检查”与“全义务关联回执”，不再使用“没有可用操作数”。
- 证据：`tests/test_dh03b_diagnostic_text.py` 的计数与范围测试；160 份真实输出统计：591 条未完成义务中“没有可用操作数”出现 0 次；158 条“未完成子检查无操作数但有其他已完成回执”均写明全义务范围；83 条重复引用全部按不同事实去重；诊断/全义务计数与回执数据 0 处不一致（`<EVID>/f6_text_stats.json`）。
