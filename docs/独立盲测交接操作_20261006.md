# 独立盲测交接操作

本包用于准备材料和签认流程，当前没有独立人工真值，不能据此宣布业务验收通过。第十三轮处理的新官方原件及其 AI 审校结果均属于开发验证材料，禁止改标为独立盲测。

第十四轮完整 21 页原始扫描超时、校正缓存读回入库失败的旧服务回执不能作为新冻结版本的准入证据。本轮修复后须先完成下列技术准入，再交给实际独立人员。技术自检通过、交接门禁 ready、独立业务验收通过是三项不同结论。

## 已准备的内容

运行 `scripts/prepare_independent_acceptance.py --output <新的空目录>` 会生成 64 个空席位：开发、盲测各 32 个；预算/决算 × 部门/单位 × 原生/扫描八个分层，每层各 4 个。`slots.pending.json` 仅是席位，不是样本清单。`dataset.pending.json` 的 documents 保持为空。

包内包含已接触开发 PDF 的 SHA 排除清单、被测源码指纹、空白 golden/区域标注/扫描认证模板、四场景回执模板和待人工冻结记录。脚本不读取盲测标签、不创建复核人、不生成真实缺陷组、不启动生产服务，也不把 AI 标注注册为人审真值。

新增 `handoff.pending.json`、`corpus_intake.pending.json`、`technical_preflight.pending.json` 和对应模板。路径以 handoff 文件所在目录为基准；每个附件填写 `path` 和实际文件的 SHA-256。准备脚本只给已生成附件填当前 SHA，附件签认或修改后须重新计算；pending 文件不能据此转成 passed。`--known-development-root` 只增加排除来源，始终保留仓库的 samples、corpus、outputs 三个默认来源，并同时识别 `.pdf`/`.PDF`。SHA 排除只是已知范围，仍须独立人员完成近重复和访问审查。

第十三轮旧准备包保留不变。本轮新准备包位于 `outputs/remediation_20261007_round15/independent_intake_final/`；其 `preparation_receipt.json` 和 `code_manifest.json` 是技术准备记录。`freeze_record.pending.json` 中自动填入的源码、模型、评测器 SHA 只是机器测得身份，人员、冻结时间与签认字段仍为空。

## 材料保管与独立签认

1. 由实际材料保管人选择未用于当前开发的新官方原件，保存完整文件、来源 URL、下载时间、原件 SHA、文种、年度、发布单位及分层理由。原始扫描必须是官方发布的扫描文件；原生 PDF 渲染图、合成控制、截取的两三页材料不计完整原始扫描。
2. 比对 `development_exclusions.json`，拒绝已见原件的 SHA 重用。近重复还须由独立人员检查：同一单位/年度的修订稿、改封面、不同分辨率扫描、同表换格式、开发样本的轻微改字版本都可能泄漏。将组身份、判定理由和分歧处理写入近重复复核附件并固定 SHA。
3. 实际标注人员直接检查原件，先确定完整适用检查分母，再标注缺陷、可接受项和待复核项。每个真实缺陷组用明确 `truth_group_id`；多条证据用不同 `annotation_id`。盲测至少 100 个经独立复核的真实缺陷组，不能凑满 100 条重复引用。
4. 每个缺陷区域标注物理页、PDF 点坐标 bbox、原文引文、期望值及严重度；不确定的单位、年度或来源列入 manual_review。适用关系填入 `applicable_sub_checks`，不得根据系统执行结果反推或删减分母。分歧由实际独立复核者解决并签认，保存附件与 SHA。
5. 扫描引用认证按 [ZC07 数据格式](ZC07_真实验收数据格式.md) 的装配说明填写。记录、原件图像及裁剪 SHA、原始预测身份必须逐引用绑定；没有独立签认的候选裁剪包不能成为认证清单。golden 的扫描认证路径/SHA和部署环境的路径/SHA分别配置。
6. 保管人封存盲测真值；开发会话在被测代码冻结前不得接触。填写真实人员、冻结时间、源码/配置/模型身份、访问记录和签认附件。当前开发材料的 AI 审校不能代替这一步。

## 人员和准入交接

将实际人员 ID 填入 handoff 的 `roles`：developers（开发）、custodians（保管）、annotators（标注）、independent_reviewers（独立复核）、executors（执行）。开发人员不得兼任独立角色；标注者不得作为自己的独立复核者。保管人与执行者可由同一实际独立人员承担，但须在签认附件中明示职责、标签权限和权限变更时间。不要填写虚构姓名、AI 会话或脚本名。

`role_signoff` 为 JSON 签认索引，含 `status: signed` 和与 handoff 完全一致的 roles；真实签名/人员授权资料由保管人另行留存。`access_review` 必须含 `status: signed`、实际独立复核者 `reviewed_by`、`blind_truth_access_before_code_freeze: false`，并附实际访问审查依据。`near_duplicate_review`、`disagreement_review` 分别含 `status: signed`、`resolved: true`、`reviewed_by` 和覆盖全部入库文档的 `doc_ids`；详细分组、分歧和审定理由仍需实际人员填写。`freeze_signoff` 含 `status: signed`、custodian 和 reviewed_by，与 roles 中实际人员一致。

`corpus_intake` 不含标签正文，每条 documents 记录采用 document-row 模板：doc_id、八层身份、`source_pdf: {path, sha256}`、official_original、complete_original、source_url、带时区 downloaded_at、near_duplicate_group。同 SHA 原件不得重复；近重复组不能跨 development/blind。开发和盲测每层至少 4 份，盲测真实缺陷组数量由实际人员在 `blind_defect_groups_attested` 签认，解封后的评测器仍须重新计算真实分组，声明数量不能代替计算结果。

`truth_seal` 指向实际封存真值包；准入检查仅计算其字节 SHA，不解析标签。freeze_record 填 `status: frozen_signed`、truth_sealed_at、code_frozen_at、无提前接触声明；真值先封存，再冻结代码。frozen_identities 提供实际源码清单、模型清单、配置、评测器、数据集公开清单、人工覆盖层清单的路径与 SHA；与 freeze_record 的身份逐一吻合。没有人工覆盖层也应保存空覆盖层清单并固定 SHA，不能留空或把两次运行的不同覆盖层视作相同版本。源码清单包含未提交修改的文件 SHA，不能只用 Git HEAD 代替。

技术准入采用 [technical_preflight 模板](acceptance_templates/technical_preflight.template.json)，引用本次真实服务 run 的回执、原始状态 JSON 和日志，必须满足以下要求：

- 完整原始扫描预算：保留官方完整原件，原件 SHA 和 PDF 实际页数一致；processed_physical_pages 覆盖每一物理页；原始 result.checksum 绑定原件；OCR pages 中每页 ok 为 true 且 failed_pages 为空；Worker 在明确的有限预算内结束并形成 analysis_revision。保留逐阶段 trace、实际耗时、API/Worker/OCR 身份和清理回执。不可截页、跳 OCR、使用原生 PDF 渲染替身或仅扩大客户端等待。
- 完整混合决算缓存校正：保存 initial 和 corrected 两版原始 result，两个 `meta.structured_ingest.status` 均为 done，校正后的 `meta.structured_ingest.parse_cache_hit` 必须为 true；job_id、analysis_revision、parse_run_id、document_version_id 及 source_sha256 与实际数据库当前版本查询对应。仅相同 parse_run_id 不证明读过缓存。warning、error 或缺少本次回执均不通过此准入；低质量输入仍可留作开发人工复核案例。
- PostgreSQL 查询回执采用 [current_ingest_query 模板](acceptance_templates/current_ingest_query.template.json)，按结果中的 parse_run_id/document_version_id 限定查询，记录事实及证据数量和查询时间。analysis_revision 填 analysis_results.raw_response 的 result_revision 字符串，与 status 中的 rev-* token 一致；analysis_jobs.analysis_revision 的整数只是数据库计数，不可替代该 token。校正后记录目标真实金额 fact_uid、evidence_ids，以及原始解析金额和当前校正金额各自的来源。原始 parse_facts/parse_evidence 是不可变解析基础，不能要求缓存校正把原金额覆盖为新值。`corrected_fact_rows` 表示当前版本的校正投影视图：original_database_rows 附真实 database_receipt JSON（job、result_revision、result_ingest_status、parse_run、run_facts_count、run_evidence_count、target_original_facts、target_original_evidence）；correction_ledger 附原样持久化 corrections.jsonl；fact_context 附当前版 fact_context.json，三项均有路径和 SHA。门禁核对原始行和证据、当前数据库结果 token、同版本 status.meta.fact_context 的来源/解析身份/版本 token、由事实重算的 Context token、JSONL 的原分析基准及目标/值/证据，以及 Context 已消费的覆盖层。此准入场景须体现一次真实金额改值且保留原金额；手填投影行、空台账、借用旧版 Context 均不通过。该字段不能伪称为直接查询 parse_facts 得到的新金额。服务复验须在清理临时工作区前原样保存台账和 Context，不能事后重建。禁止用全库非零 counts、此前成功任务或栏次编号充当本次校正入库成功。cache_readback 附件记录实际缓存命中、对应 parse_run_id、JSONB 单元格 provenance 已解码的观测，保留原始查询/日志，不能只手填自报布尔。
- service_receipt 必须 passed、cleanup complete、运行期间源码未变。其 code_fingerprints 必须与冻结源码清单对应。凡原审/校正入库 error、原始扫描超时或清理未完成，整次准入失败；修复后用新输出目录复跑，旧失败证据继续保留。

```bash
.venv/bin/python scripts/prepare_independent_acceptance.py \
  --check-handoff /absolute/path/handoff.json \
  --stage intake \
  --check-report /absolute/path/intake-gate-run-01.json
```

退出码 0 仅表示交接附件结构及已声明身份通过完整性检查；退出码 2 表示不完整。门禁不会认证签名真伪、验证官方链接真实性或证明访问记录完整，实际独立人员须对这些内容负责。`business_acceptance` 固定为 not_evaluated，不提供伪造业务指标。

## 冻结后执行

独立验收者将实际原件与已签认 golden 装配至隔离验收工作区的 `corpus/<doc_id>/`，将实际文档记录写入 dataset 清单。保留原工作区和既有 golden，不覆盖旧证据。完整运行原生预算、带冻结已知缺陷的原生决算、原始完整扫描预算、完整混合决算人工校正四场景；所有场景走真实 API、独立 Worker、隔离 PostgreSQL，涉及扫描者还须实际 OCR。

同一冻结源码、配置、模型、原件和人工覆盖层执行两次，保存生产回放、逐项回执、事实/证据身份及 JSON/CSV/DOCX/PDF。先冻结系统输出，再由保管人解封真值；独立评测人员记录解封签认。校正场景保存前后版本、受影响关系和旧版下载隔离证据。

```bash
.venv/bin/python scripts/run_zc07_acceptance.py \
  --manifest /absolute/path/dataset.json \
  --e2e-evidence /absolute/path/e2e.json \
  --mode legacy \
  --output /absolute/path/acceptance-run-01.json
```

第二次必须使用相同冻结身份和新的输出路径，并提供 `repeat_replay_path` 与可信 `repeatability_basis`。真实清单、认证、适用分母或四场景缺失时，门禁仍不通过，相关业务指标保持 null/not_computable。

两份回放顶层各保存实际服务的 run_id 和带时区 executed_at（从本次运行日志采集），run_id 与时间均须不同。重复回放不能指向同一物理文件、软链接或硬链接，也不能把同一次运行复制到新路径后改名作为重跑。不同独立运行产生相同业务内容属于有效邻例，评测按规范化内容比较，不因内容相同拒绝。逐文档 applicable_sub_checks 必须为非空、合法且不重复的冻结关系清单；某份文档的空清单或无效项会使整体完成率不可计算，不能被其他文档的 pass 回执覆盖。

每次输出冻结采用 [output_freeze 模板](acceptance_templates/output_freeze.template.json)，保存唯一 run_id、带时区 frozen_at、全部盲测 doc_id、六项冻结身份和 output_manifest。output_manifest 的 documents 对每份盲测原件分别保存 doc_id、analysis_revision、replay 附件和 `exports.json/csv/docx/pdf` 四个附件，各自有实际路径及 SHA。同一 run 的同一附件不可在冻结后覆盖；第二次运行另建目录。文件 SHA 证明冻结内容未变化，重复运行是否业务一致仍由正式评测器比较规范化回放、证据身份和四格式内容，不能只比较计数。

handoff 的 output_freezes 提供两份输出冻结索引；truth_release 提供真实保管人签认的 JSON，含 `status: signed`、custodian、released_at。两次输出冻结时间均须晚于 code_frozen_at 且早于解封时间。先运行执行交接门禁，再由独立评测人员读取已解封真值进行 ZC07 正式评测：

```bash
.venv/bin/python scripts/prepare_independent_acceptance.py \
  --check-handoff /absolute/path/handoff.json \
  --stage execution \
  --check-report /absolute/path/execution-gate-run-01.json
```

若冻结后修改源码、模型、配置、原件或覆盖层，原冻结身份失效，须新冻结、新跑两次；已解封材料转为开发材料，不能直接沿用作新的未接触盲测。独立人员须重新选择未暴露材料或明确停止以独立盲测名义报告。

当前尚待实际保管人/标注人/独立复核人/执行者、64 份新材料、完整人工分母及真值、至少 100 个独立真实缺陷组、区域认证和实际签认附件。自动准备、自检和 AI 观察不能补齐这些人类输入，也不能宣布独立盲测完成。

保留门槛：正式问题精确率≥98%、真实缺陷召回≥95%、重大问题零漏报、精确定位≥98%、证据真实性100%、越界定位0、确定性适用检查完成≥95%、状态/原因覆盖100%、四格式和同版本重复运行100%一致。不能用模型分数或 pytest 数量替代业务指标。
