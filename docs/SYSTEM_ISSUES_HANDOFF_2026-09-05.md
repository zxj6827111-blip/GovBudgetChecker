## 3. 系统问题分类清单（复查重点）

### 3.1 表格语义解析缺陷在**规则层**，不在底层 PDF 抽取器（最高优先级，产生 12 条假 findings，含 4 条假 error）

**v2 修正落点**：GPT-5.6 复核确认——底层抽取器（`src/services/pdf_page_extract.py:17`）能正确读出 P7 的 `["总计","4,733.14","总计","4,733.14"]` 与 P15/P16 的主要行。真正破坏语义的是规则层：

**A. `_parse_row_values()` 把非数值单元格转成 0.0 + 按位置猜列**（`src/engine/rules_v33.py:2162`）
- 该函数签名 `"""解析行中的所有数值，空值视为0"""`，非数值单元格（「项目」「总计」「收入总计」等行标签）一律转 `0.0`，随后按列位置对号——**「收入总计(0.0)」的 0.0 直接来源于行标签文本被转零**。
- 直接后果：V33-115 两条假 error（`rules_v33.py:2206`）「总表平衡性错误：收入总计(0.0) != 支出总计(4733.14)」「收入侧平衡错误：计算值(4733.14) != 文档值(0.0)」——表文本身完全平衡。
- 修复方向：单元格应保留 `number/text/bbox` 三态（非数值为 None 而非 0.0），金额用 Decimal；行标签与数值列的对应应由**表头命名列**驱动，而非固定位置索引。

**B. V33-117 合计行归属错位**（`src/engine/rules_v33.py:2478`）
- 假 warn「人员经费校验失败：显式合计(416.36) != 分项之和(3309.02)」「公用经费=416.36 != 1129.37」。
- 机制（GPT-5.6 复核）：P15/P16 是左右双栏经济分类布局，明细行中重复出现的 301/302/303/310 被当作**类级合计行**重复累加，类款编码「301 01」中的「01」被误读为金额——导致 3309.02/1129.37 这两个与任何真实口径都对不上的累加值；真实：301 类 2,857.05 + 303 类 91.97 = 2,949.02（人员经费合计）；302 类 401.93 + 310 类 14.43 = 416.36（公用经费合计）。
- 修复方向：需要 §6 的统一表格中间层（`row_role: detail/subtotal/total`、`code_domain`）才能根治。

**C. V33-120 跨页列宽/合计列索引漂移**（`src/engine/rules_v33.py:2372`）
- 4 条假 warn「层级校验失败(211): 父级金额(0.0) != 子级之和(2199.25)」等。
- 机制：不是底层「漏行」——是跨页合并（`rules_v33.py:2140` 附近的续读逻辑）在两页列宽不一致时**合计列索引漂移**，部分行的金额取到 0.0/错值。子级之和 161.02 = 7.50+30.50+123.02 恰好缺 1,293.60、88.60 两款项，即漂移漏取的直接表现。
- 修复方向：跨页只在表头模式兼容时合并；父级取值失败时降级 `manual_review` 而非确定性 warn。
- 注意：V33-117 在代码中 severity 为 "error" 而实际输出 warn——存在后处理改写严重度的路径（`src/engine/rule_adapter.py` / `src/services/rule_findings.py`），复查时需一并厘清。

**D. 说明↔表对照的解析失败** —— 规则 V33-220（`src/engine/rules_v33.py:4151`）
- 2 条假 warn「说明3↔T3基本支出不一致：说明=4733.14, 表内未找到对应值（行数据全 0.0）」。
- 证据：说明三原文「基本支出**3365.38** 万元，占71.10%；项目支出**1367.76** 万元」——系统把本年支出合计 4733.14 误当成基本支出的说明值；《支出决算表》合计行真实值是 4,733.14 / 3,365.38 / 1,367.76，不是全 0。说明解析与表格解析**双重错位**（同属 §6 第 4 条「说明文本归因」要解决的问题）。

### 3.2 数字归因/配对错误（4 条，其中 2 条假 error）

**A. 三公分项数字错配** —— 规则 V33-244（`src/engine/rules_v33.py:3427`）
- 假 error「【表七】因公出国决算表文不符：报表(0.00) != 说明(16.95)」「公务接待：报表(0.00) != 说明(5.07)」
- 证据：说明原文「因公出国（境）费支出决算为**0.00** 万元」与表一致；16.95 是同段落三公合计/公车决算数，5.07 是同比增加额，被错配到分项名下。
- 复查方向：说明段落的数字→分项归因逻辑（「其中：因公出国（境）费…」句式解析）。

**B. 跨句数字配对** —— 规则 V33-110（`src/engine/rules_v33.py:1693`）
- 假 error「预算数4628.17，决算数51.98，实际小于，但文本表述为大于」
- 证据：总述句「年初预算为 4628.17 万元，支出决算为 **4733.14** 万元，完成年初预算的 102.27%。决算数大于预算数…」本身正确；51.98 是下文第一个分项（行政单位离退休）的决算数，被跨句配对到 4628.17。

**C. 年份当数字** —— 规则 V33-106（`src/engine/rules_v33.py:1516`）
- 假 warn「一般公共预算财拨支出合计(1367.75)与总体情况说明数字(**2025.00**)不一致」——「2025年度」的年份被解析成数字 2025.00。
- 附注：这条背后有真问题的影子（1367.75 是 P14 表合计，说明写 1367.76，差 0.01，见真值 T2/T3），但系统报告的理由完全错误。若修好归因，此规则应能捕获 0.01 尾差（是否报取决于容差设计，见 §3.4）。

### 3.3 规则设计缺陷（38 条批量误报，占 73%）

**A. CMM-004 未区分经济/功能分类科目域**（`src/engine/common_rules.py:494`）—— 33 条
- 「类款项编码 301/301xx/303/303xx/310/310xx 仅出现在支出表」。这些是**经济分类科目**，只出现在经济分类性质的《一般公共预算财政拨款基本支出决算表》（P15）是**正常且必然**的。
- 修复方向：建立科目域识别（301-310 经济分类 vs 101-229 功能分类），经济分类编码不参与跨表镜像检查。仅此一条规则修复即可消除 63% 的误报。
- 该规则是 Golden Corpus 规划里的高频规则（历史 793 任务中 91 条），修复影响面大，需回归。

**B. CMM-002 中文引号误判**（`src/engine/common_rules.py:307`）—— 4 条
- 「疑似多余右引号」命中了正常中文引号：「机构设置”）」「十五五”规划》」「合格”的项目」「入”、“经营收入”」。全文右引号均有配对左引号。
- 修复方向：归一化层把全角引号视为正常标点；或该规则只针对引号数量失衡（同段右引号 > 左引号）。

**C. V33-001 未排除同比引用**（`src/engine/rules_v33.py:493`）—— 1 条（error）
- 「2025 年报告中出现 2024 年内容」命中了「与2024 年度相比…增加 90.09 万元」——决算说明的同比表述是**必需内容**，不是年份混淆。
- 修复方向：排除「与…相比」「较上年」「同比」等同比语境；或在决算报告类型下直接禁用该规则（同比必提上年）。

### 3.5 AI 未执行被呈现为「AI 已运行且报 0」（v2 修正，P0）

**v1 错误**：v1 沿用 2026-08-29 的结论称「AI 调用返回 0 条，复现已知根因」。**GPT-5.6 复核推翻**：本次 AI **根本没有执行**。

证据链：
1. `result_meta.dual_mode_enabled: False`、`mode: "legacy"`——任务走 legacy 纯规则路径；
2. legacy 路径 `run_rules()`（`src/engine/pipeline.py:66`）里 `rule.apply_with_ai(doc, use_ai_assist)` 的基类默认实现（`src/engine/rules_v33.py:474`）就是 `return self.apply(doc)`——**不调用任何模型**；
3. `result_meta.provider_stats: []`、无 model_versions——没有可证明的模型调用记录。

**问题实质**：`use_ai_assist=true` 的标志位与实际行为不符，结果里没有任何「AI 未运行」的显式状态——使用者无法区分「AI 查过没发现问题」「AI 没查」「AI 失败降级」三种情况。

**修复方向（AI 状态机）**：引入 `not_requested / not_run / succeeded / degraded / failed` 五态；没有调用记录、模型版本和 token 统计时**禁止**呈现为「AI 已完成」。`max_tokens=3200` 写死（`src/engine/ai/extractor_client.py:433`）与输入表征缺失仍是真实隐患（2026-08-29 dual mode 实测结论仍有效），但在状态机落地前无法被观测。

### 3.6 「假完成」质量门缺陷（v2 新增，P0，比误报更严重）

本次任务存在三项应当阻断「done/complete」终态的信号，全部被丢弃，最终仍返回 done/complete：

1. **结构化入库缺核心表**：`structured_ingest.review_items` 里系统**自己已经发现** `FIN_05_general_public_expenditure:missing`（type=missing_core_table，severity=warn，recommended_action=review_missing_table）——即《一般公共预算财政拨款支出决算表》未被识别入库。信号存在但被丢弃。
2. **规则证据不完整**：`evidence_completeness` 显示 52 条中仅 **40 条完整、12 条 incomplete**（全部 missing_page，来自 V33-115/120 等解析错位规则），但质量门只接收 `evidence_degraded_count`（本次=0，因为不完整≠降级），不完整数没有进入门禁。
3. **报告类型错分**：上传 `doc_type=dept_final`，`_normalize_report_type()`（`src/services/ps_schema_sync.py:411`）只认识 `{"budget","预算","ys"}` / `{"final","决算","js","settlement"}`，`dept_final` 不在其中 → **默认写库为 BUDGET**（`ps_sync.report_type: "BUDGET"` 实证）。决算材料以预算身份入库，是明确的数据归类错误。

**代码落点**：`_evaluate_quality_gate()`（`api/main.py:446`）的 6 个触发条件（页面覆盖率/扫描页/unknown 类型/年度/AI 必需失败/证据降级）**不接收**结构化缺表、规则证据不完整、报告类型错分三类信号。

**修复方向**：上述三类信号必须进入 `review_reasons`，命中即转 `review_required`；同时把 `dept_final/dept_budget` 等前端 doc_type 值补进 `_normalize_report_type` 的映射（或统一枚举）。质量门的设计意图（docstring 自述「避免扫描件静默漏检却显示审核通过」）是对的，缺的是接线。

## 4. 工程环境问题（非检查质量，但影响开发体验）

1. **测试隔离缺陷（已修，随批次一未提交）**：`tests/test_ai_client_config.py:16` 未清理 `AI_FALLBACK_CHAIN`，套件内其他测试导入 `api.main` 触发 `load_dotenv()` 把 `.env` 的值注入进程导致本地必挂。已加 `monkeypatch.delenv` 修复。**同类隐患**：conftest 只对 `DATABASE_URL` 有 autouse 摘除，AI_*/GOVBUDGET_* 等变量仍靠各测试自觉，建议统一做敏感变量摘除 fixture。
2. **Makefile 与 .env 的 key 漂移**：`make backend` 传 `GOVBUDGET_API_KEY=dev-local-key`，而前端 `app/lib/backendAuth.ts` 优先从根 `.env` 读 `GOVBUDGET_API_KEY`——两者不一致时代理链路 403 invalid_api_key（本次实测踩中）。本地起服务应统一走 `.env`；Makefile 默认值建议改为提示或对齐。
3. **IAB 内嵌浏览器限制**（工具环境，非系统缺陷）：ZCode IAB 对 React 受控表单的事件注入失效（locator click 卡 actionability、dom_cua/cua 点击键入均无效）、截图不可用。GUI 走查用 e2e（真实 Chromium）或人工完成。
4. **批次一修改未提交**（运维风险，最大丢失面）：24 个文件 D/M + `app/app/api/metrics/`（未跟踪的新代理路由）+ 7 份文档 untracked，全停在工作树。
